# Lab 2 Reflection: How the Context File Shaped Agent Behavior

The before/after test in [`Lab2_ContextComparison.md`](Lab2_ContextComparison.md) used one task — "write a `SellStockUseCase`" — with and without `CLAUDE.md`. Without it, the agent produced internally consistent, reasonably well-engineered code that was simply wrong for this codebase: an invented package, a repository interface with methods that don't exist, `BigDecimal` where this project uses `double`, and a custom result type standing in for the real `ResultCallback<T>`. That's not a bad guess — it's the correct generic answer to an underspecified prompt. "Sell part of a holding" has no single correct implementation in the abstract; it only has one *in this repository*, and that information lives in the code, not the task description.

With `CLAUDE.md`, the agent got much closer: the real package, the real classes, the project's validate-then-delegate pattern, errors reported through the callback instead of thrown, and even the `double`-plus-epsilon convention for quantity comparisons — a detail the file never states directly but that was inferable once the agent understood the codebase uses `double`, not `BigDecimal`. But closer wasn't correct. The real compile check in `Lab2_ContextComparison.md` found that Instance B fails to compile too, on two specific facts `CLAUDE.md` simply didn't document at the time: that every `PortfolioRepository` method is scoped by a leading `userId`, and that `StockHolding` is immutable with no setters. `CLAUDE.md`'s UseCase convention section described the shape of a call — raw-string params, validate-then-delegate, `ResultCallback<T>` — but not these two interface details, so an agent reading it carefully still had no way to get them right. That was a real gap in the file's content, not a failure of the agent's reading, and the original version of this reflection understated it by not saying so.

The real value of `CLAUDE.md` isn't catching typos — a non-compiling class is caught by the build either way. It's preventing *silent* architectural drift: code that compiles fine but quietly introduces a second error-handling convention or numeric type, which nothing forces anyone to notice until two inconsistent patterns have already spread through the codebase. Instance B showed that benefit partially, not fully — getting the shape right while still missing interface specifics the file never stated.

One honest limitation: this test only shows the agent can follow conventions when handed the file — not that it would find `CLAUDE.md` unprompted. That depends on the surrounding tooling (this project's sessions do read it automatically), not the file's content.

## Re-run after the CLAUDE.md fix (2026-10-04)

The two missing facts above were added to `CLAUDE.md`'s UseCase convention section as two new bullets: every `PortfolioRepository` method takes `userId` first, and `StockHolding` is immutable — construct a new instance (e.g. via `withId(...)`) rather than calling a setter. To check whether that actually fixes anything, rather than assuming it would, the same blind-generation method was re-run: a fresh agent instance, zero prior conversation history, no file access, given only the task sentence plus the full updated `CLAUDE.md` text, asked to produce "Instance B (revised)" with no hint about what the previous compile check found.

Instance B (revised) passed `userId` as the first argument on every `getHoldings`/`updateHolding`/`deleteHolding` call, and built a new `StockHolding` instance instead of calling a setter — both matching the two new rules. Compiled for real against this repository's actual `StockHolding`, `PortfolioRepository`, and `ResultCallback` (after a mechanical package-prefix correction unrelated to either rule — `CLAUDE.md`'s architecture diagram shows the `domain/model/repository/usecase` directory layout but never states the `com.portfolioiq` root package explicitly, a separate, pre-existing gap this re-run wasn't testing), the error count dropped from 4 to 1, and neither of the two originally-targeted errors was among the ones that disappeared by accident — both are gone specifically.

The one remaining error is a different, previously-hidden one: the agent guessed a `StockHolding(ticker, quantity, purchasePrice, purchaseDate)` constructor with a `getPurchaseDate()` getter, neither of which exists — the real constructor is `StockHolding(String id, String ticker, double quantity, double purchasePrice)`, with no purchase-date field at all. `CLAUDE.md` still doesn't document the model's actual constructor signature or getters anywhere, only that it's immutable, so this was unreachable from the file as it stands.

Honest reading: the two added rules worked, precisely and only on what they targeted — this is real, re-run evidence, not an assumption. The natural further step this surfaces, not yet done, is to also document `StockHolding`'s real constructor and getters in `CLAUDE.md` and re-run a third time to see whether that closes the last gap. Full compiler output for this re-run is in `PortfolioIQ_Lab2_Evidence.pdf`.
