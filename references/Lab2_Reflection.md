# Lab 2 Reflection: How the Context File Shaped Agent Behavior

The before/after test in [`Lab2_ContextComparison.md`](Lab2_ContextComparison.md) used one task — "write a `SellStockUseCase`" — with and without `CLAUDE.md`. Without it, the agent produced internally consistent, reasonably well-engineered code that was simply wrong for this codebase: an invented package, a repository interface with methods that don't exist, `BigDecimal` where this project uses `double`, and a custom result type standing in for the real `ResultCallback<T>`. That's not a bad guess — it's the correct generic answer to an underspecified prompt. "Sell part of a holding" has no single correct implementation in the abstract; it only has one *in this repository*, and that information lives in the code, not the task description.

With `CLAUDE.md`, the agent stopped guessing and started matching: the real package, the real classes, the project's validate-then-delegate pattern, errors reported through the callback instead of thrown, and even the `double`-plus-epsilon convention for quantity comparisons — a detail the file never states directly but that was inferable once the agent understood the codebase uses `double`, not `BigDecimal`. That's the most useful part: the file didn't just supply facts to copy, it supplied enough of the project's shape to extend the pattern correctly to a case it never mentioned.

The real value of `CLAUDE.md` isn't catching typos — a non-compiling class is caught by the build. It's preventing *silent* architectural drift: code that compiles fine but quietly introduces a second error-handling convention or numeric type, which nothing forces anyone to notice until two inconsistent patterns have already spread through the codebase.

One honest limitation: this test only shows the agent can follow conventions when handed the file — not that it would find `CLAUDE.md` unprompted. That depends on the surrounding tooling (this project's sessions do read it automatically), not the file's content, which did its job here.
