# Lab 2 Reflection: How the Context File Shaped Agent Behavior

The before/after test in [`Lab2_ContextComparison.md`](Lab2_ContextComparison.md) used the same one-sentence task — "write a `SellStockUseCase`" — with and without `CLAUDE.md` in the prompt. Without it, the agent produced code that was internally consistent and reasonably well-engineered, but wrong for this codebase in ways that would fail at compile time: an invented package, a repository interface with methods that don't exist, `BigDecimal` where this project uses `double`, and a custom result/error type standing in for the real `ResultCallback<T>`. None of that is a bad guess — it's the correct generic Java answer to an underspecified prompt. The problem is that "sell part of a stock holding" has no single correct implementation in the abstract; it only has one correct implementation *in this repository*, and that information lives in the code, not in the English description of the feature.

With `CLAUDE.md` in the prompt, the agent stopped guessing and started matching. It used the real package and the real classes, followed the raw-string/validate-then-delegate pattern every other use case in the project follows, reported errors through the callback instead of throwing, and even picked up the `double`-plus-epsilon convention for quantity comparisons — a detail that isn't stated as a rule anywhere in `CLAUDE.md` but was inferable once the agent understood it was working inside a codebase that uses `double` for `StockHolding.quantity` rather than `BigDecimal`. That's the most useful part of the result: the context file didn't just supply facts to copy, it supplied enough of the project's shape that the agent could extend the pattern correctly to a case the file never explicitly mentioned.

The practical takeaway for this project is that the value of `CLAUDE.md` isn't in preventing typos — it's in preventing *silent* architectural drift. A generated class that doesn't compile gets caught immediately by the build. A generated class that compiles fine but quietly introduces a second error-handling convention, a second numeric-type choice, or a parallel repository interface is far more dangerous, because nothing forces anyone to notice until two inconsistent patterns have already spread through the codebase. That's exactly the gap `CLAUDE.md`'s "UseCase convention" and "Coding standards" sections are meant to close, and this test is the first real evidence that they do.

The one limitation worth naming honestly: this test only checked whether an agent given the context file *could* follow the codebase's conventions when explicitly handed them in the prompt. It didn't test whether an agent would reliably go find and read `CLAUDE.md` on its own if it weren't handed to it — that depends on the tooling around the agent (this project's own Claude sessions do read it automatically at the start of a task), not on the file's content. The content itself, at least on this one test, does what it's supposed to do.
